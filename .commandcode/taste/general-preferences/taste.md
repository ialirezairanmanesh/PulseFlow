# General Preferences
- Expects the agent to autonomously explore/inspect the whole project first (list files, read docs and source) before answering, rather than asking clarifying questions up front. Confidence: 0.55
- Wants review/improvement output framed from a role perspective (e.g. "as a tester and as a Flutter developer") and delivered as concrete, prioritized, actionable proposals — not just a description of the code. Confidence: 0.5
- Works primarily in Flutter/Dart and prefers suggestions that leverage ecosystem packages and idiomatic Dart/Flutter project structure (pub packages, proper lib/src layout, dev_dependencies). Confidence: 0.5
- Uses VS Code and manages Flutter run configurations in `launch.json`; expects dedicated launch entries per mode (default, `flutterMode: "profile"` with `--enable-dart-profiling`, and `flutterMode: "release"`) rather than a single config. Confidence: 0.5
- Organizes the Flutter codebase as a monorepo of separate packages: feature packages under `modules/<feature>` and shared packages under `shared/<name>` (core, api, components, analysis); launch configs are set up per package via `cwd`. Confidence: 0.5
- Runs behind the Great Firewall / uses China mirrors — configures `PUB_HOSTED_URL=https://pub.flutter-io.cn` and `FLUTTER_STORAGE_BASE_URL=https://storage.flutter-io.cn` for pub access. Confidence: 0.45
- For larger, multi-part changes, wants a structured, complete and detailed written plan agreed on before any code is written, then execution against that plan (asked to "make a plan and start doing it", then for the next phase a plan that is "complete and detailed"). Confidence: 0.6
- Prefers simple, memorable repo-root dev entry points: a convenience launcher script (e.g. `run.sh`) plus a top-level Makefile with a simple target (e.g. `make run`) to build/run the whole project, instead of remembering raw commands or relying on npm scripts alone. Confidence: 0.6
- When moving to a next phase/milestone, wants the agent to first restate what that phase entails and explicitly wait for a go-ahead before starting work, rather than proceeding autonomously. Confidence: 0.6
- Once a concrete list of remaining/pending items has been presented, prefers the agent to resolve them all end-to-end ("from start to finish") rather than asking the user to pick one to start with; dislikes being asked to choose among known outstanding tasks. Confidence: 0.5
- When asked to plan a phase/milestone, wants not just the plan but the complete, self-contained, copy-paste-ready prompt that can be handed to a fresh session/agent to implement it (explicitly: "write the plan and give me its full prompt"). Confidence: 0.6
- Expects multi-phase feature plans to be written out as reusable markdown plan files (e.g. under `~/.commandcode/plans/`) that the implementation then references and follows. Confidence: 0.5
- Prefers each new implementation phase to be executed in a fresh, separate chat/session (independent context) rather than in the current thread — e.g. asked to "open a new chat" and do the work there. Confidence: 0.5
- Wants tools/features to produce a self-contained, exportable output artifact (e.g. copy-to-clipboard or downloadable Markdown/JSON) that can be handed off to external AI agents for review, not just data visible in the UI. Confidence: 0.45
- Security-minded about secrets: prefers API keys/tokens stored server-side (git-ignored) and proxied through the app's own backend so they are never exposed to the browser/client, with keys redacted from responses and errors. Confidence: 0.6
- Prefers local/on-machine Android testing via containerization (redroid/Android-in-Docker) with separate containers per build mode (debug/profile/release), managed through convenience scripts (`redroid.sh`) and Makefile targets rather than manual Docker commands or remote/cloud devices, so they can test across all modes easily on the same machine. Confidence: 0.65
- Prefers integrations to be provider-agnostic — supporting multiple providers (e.g. OpenAI-compatible with configurable base URL, Anthropic, Gemini) via a settings page rather than being locked to a single vendor. Confidence: 0.55
- Works on performance iteratively: wants to capture a baseline session, apply fixes, re-measure, and get an explicit before/after comparison report (metric deltas plus what got fixed, what regressed, and what persists) rather than only a snapshot of the current state. Confidence: 0.5
- Prefers explicit user-selectable controls over the agent guessing/hardcoding a default: when a value matters (e.g. device resolution/aspect), wants a visible selector (preset options plus a custom-value input and a swap/rotate toggle) that the user drives, rather than automatic inference or an assumed default. Confidence: 0.5
- Wants tools/integrations usable from multiple coding-agent clients and IDEs, not just one — expects a ready per-client config file checked into the repo (e.g. repo-root `.mcp.json` for Command Code, `.cursor/mcp.json` for Cursor) using `${workspaceFolder}` or absolute paths, plus concise step-by-step usage instructions. Confidence: 0.5
- Wants user-facing documentation kept in sync with new capabilities: expects added features to be documented in the published package docs (the README that pub.dev renders), not only in-repo files or the internal CHANGELOG. Confidence: 0.45
- Judges generated prompts/AI output by whether it is "execution-ready": explicitly dislikes vague, generic advice and wants exact targets named (specific widget/class, file:line, route/screen), the precise API/pattern to add/change/remove, and short before→after snippets grounded in the measured data — plus a defined output-format contract so the model can't drift. Confidence: 0.55
- Wants user-facing docs written from the perspective of a first-time end user (e.g. someone who just found the package on pub.dev), i.e. self-explanatory and step-by-step: state what the feature is and link it, list prerequisites, give exact register/setup commands per client, then a concrete "how to use it" example — rather than jumping straight into config assuming the reader already has context. Confidence: 0.6
- Wants key capabilities discoverable from the landing/README page (e.g. a short pointer/section near the top that links down to the details) so a new visitor can find them without prior knowledge of the repo. Confidence: 0.55
- Wants package changes shipped to the public registry (pub.dev): after doc/README or feature updates, expects the package to also be published/released there, not just committed to git (explicitly approved "publish it on pub too" for the Flutter package after the docs update). Confidence: 0.6
- Prefers to apply changes to their own environment/personal app configs (e.g. global editor MCP settings) themselves: wants just clear copy-paste instructions, and does not want the agent to directly edit/merge those personal or global config files on their behalf. Confidence: 0.8
- Evaluates setups/docs by whether any pub.dev consumer could add and use the tool easily, not just the current user's machine — expects the agent to always keep that public-consumer perspective (minimal steps, no local-only absolute paths or assumptions) rather than configuring things for the user directly. Confidence: 0.7
- Prefers distributing tooling/CLI/MCP packages via public npm so end users can run them with a single `npx -y <package>` command — no repo clone, no absolute local paths, no manual build (agreed to publish the MCP server to npm for exactly this reason). Confidence: 0.55
- Treats "commit and push" as the standard final step after the agent finishes a batch of work — repeatedly asks to "commit and push" to `origin/main` (and approves when offered) rather than leaving changes uncommitted. Confidence: 0.75
